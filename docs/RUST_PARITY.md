## 已知语义差异（有意为之，均已记录）

- **执行批准**：WPF 持久化已批准的可执行路径（`SingBoxExecutablePath` +
  UiPreferences）；Rust 控制台每次会话显式选择，不做持久化。更保守，不是缺陷。
- **Apply 换执行文件**：Rust 控制台的 apply 固定启动时选定的可执行文件；切换需
  停止后重选。WPF 允许 apply 中途换路径。
- **瞬态进度**：WPF 有 Probing/Starting/Checking 过程状态；Rust 控制台只有最终态。
- **孤儿终止方式**：Job Object kill-on-close（托管内）与 `TerminateProcess`（恢复
  外来孤儿）对比 WPF 的 `Kill(entireProcessTree)`；sing-box 不派生子进程，语义等价。

## 升级为受支持前端前的工作清单

1. **导入/批量/AI 面板移植**（矩阵中唯一的 ❌ 项；AI 面板依赖本地 provider 协议，
   工作量约 2–3 片）。
2. **发布流水线**：release.yml 增加 Rust 控制台产物（当前 CI 已上传
   `IntentRoute-AI-rust-console` 预览 artifact）；版本号策略与 WPF 同步。
3. **签名**：与 WPF 相同的代码签名依赖（当前外部依赖未解决，两个前端同挂）。
4. **崩溃面**：eframe panic 即进程消失（WPF 有全局异常处理器写脱敏诊断）；需
   `std::panic::set_hook` 写脱敏诊断文件后退出，冒烟脚本已预留诊断读取模式。
5. **双前端共存策略**：换壳后 WPF 是否保留一段过渡期、锁互斥已天然支持两者共存
   （同目录同时只允许一个管理者）。
6. **冒烟深度**：双模式冒烟门禁已落地——窗口模式（本机/有 GPU：窗口、标题、三帧渲染
   证明、正常关闭、零退出码）与 headless 模式（CI 无 GPU runner：同一套启动/字体/
   布局 pass 离屏驱动后零退出）。如需 UIA 级断言，egui 无自动化 ID，需引入
   accessibility 支持或降级为 API 级集成测试。

## 结论建议

核心运行时与编辑语义已完全对等且互操作（锁/状态文件/配置格式三方互通）；缺口集中
在导入/批量/AI 三个面板与发布工程项。建议顺序：导入+批量面板 → 崩溃面 →
release 流水线 →（签名解决后）切换默认前端，WPF 转维护模式。
